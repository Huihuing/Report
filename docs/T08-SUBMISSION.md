## 재현·통과 확인 4가지 (권장)

**1. 어디로 가나요?** 공개 소개 `https://report-huihuing.vercel.app/`에 접속한 뒤 T08 패스키 비공개 공간 링크를 누릅니다. 비로그인 심사자는 공개 소개까지만 확인하면 됩니다.

**2. 세 단계 안에 무엇을 하나요?** ① T01 공개/비공개 경계를 확인하고 ② T08 서버의 등록·로그인 질문 및 WebAuthn 응답 흐름을 따라가며 ③ 비로그인·위조 세션 401, 허용되지 않은 Origin 403, 잘못된 서명 400, 일회용 질문 재사용 409 실제 응답과 DB 권한 차단 결과를 증거 문서에서 확인합니다.

**3. 무엇이 보이면 통과인가요?** 공개 T01과 T08 입구는 HTTP 200으로 열리고 비로그인 비공개 자료 요청은 401입니다. 서버가 등록·로그인마다 새 challenge를 주며, 이미 쓴 질문에 대한 두 번째 요청은 HTTP 409를 반환합니다. 실제 기기에서 패스키 두 개를 등록하고 하나를 지운 후 남은 것으로 로그인되는 과정도 추가 확인해야 합니다.

**4. 안 될 때는 무엇이 보이나요?** 비로그인 상태에서 비공개 메모가 페이지 소스·API 응답에 노출되거나, 틀린 서명·재사용 challenge가 통과하거나, 남의 계정 데이터를 조회하거나, 마지막 복구 패스키 없이 계정이 잠기면 실패입니다.

## AI와 내 판단 3줄 (권장)

**1. AI에게 맡긴 일:** WebAuthn 공개키 등록·서명 검증, 서버 challenge 단일 사용, 패스키 2개 관리·세션 만료, 가상 비공개 메모와 HTTP 401/409 검증 및 제출 증거를 맡겼습니다.

**2. 내가 직접 판단한 일:** 기존 T01의 공개 소개 내용은 로그인 없이 유지하고, 새 비공개 공간만 패스키로 잠그며 실제 개인정보가 아닌 가상 메모 3건을 쓰기로 했습니다.

**3. AI 제안을 따르지 않은 일:** 기기에서 수행하지 않은 패스키 등록·로그인·복구 결과를 AI의 추정만으로 통과 처리하지 않고 실제 검증 전에는 미완료로 남기기로 했습니다.

## 채점 기준상 아직 완료되지 않은 실기기 증거

- 실제 등록된 공개키(Base64URL COSE)와 기기/비밀번호 관리자의 저장 위치.
- 같은 계정의 패스키 2개 등록, 삭제 후 남은 패스키로 성공 로그인, 삭제된 패스키의 실패.
- 각기 다른 A/B 계정이 비공개 메모를 가진 상태에서 양방향 교차 조회 거절과 자료 불변.
- 실제 패스키 성공 로그인·실패 로그인 나란한 응답, 로그아웃 이전 세션 재사용 거절.
- 등록 취소 실기기 화면.

현재 SQL 검산에서 실제 T08 계정·패스키·가상 메모는 **0건**이다. 실제 기기 등록이 성공하면 자동으로 그 계정에 가상 메모 3건이 생기도록 구현돼 있으며, 등록 전부터 자료가 있다고 주장하지 않는다.

## 개인정보/비밀값

실제 연락처·상세 주소·신분증·비밀번호·개인키·세션 Bearer를 저장소와 제출문에 넣지 않는다. 실제 패스키 원문 서명은 JSON 증거에 포함하지 않고 공개키만 등록 뒤 제출 가능한 범위로 기록한다.
