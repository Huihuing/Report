## 초록

Python의 `in` 연산은 개발 과정에서 빈번하게 사용되지만, 데이터를 `list` 또는 `set`에 저장할 때 성능이 얼마나 달라지는지는 입력의 종류와 분포에 따라 달라질 수 있다. 본 연구에서는 "정수 원소가 100·1,000·10,000개 들어 있는 컨테이너에서 **없는 값**을 검색할 때, `set`의 실행 시간 중앙값이 동일 크기의 `list`보다 짧다"라는 가설을 검증했다. CPython 3.13.5이 실행되는 한 Linux 환경에서 자료구조 2종, 크기 3종, 검색 조건 3종(부재·첫 위치·끝 위치)을 30회 반복하여 **총 540개 블록 측정값**을 원자료로 저장했다. 없는 값을 찾는 경우 `list`의 중앙값은 506.80, 6,066.55, 64,935.15ns, `set`은 17.65, 18.31, 18.13ns로 관측됐다. 따라서 지정한 세 크기에서 가설이 모두 지지됐다. 반면 첫 위치 검색에서는 두 구조의 중앙값이 근접하여, 모든 검색에서 `set`을 쓰는 것이 의미 있는 향상이라는 일반화는 지지할 수 없다. 단일 장비·정수 자료·컨테이너 생성 시간 제외라는 한계를 명시하고, 원자료·실행 코드·재분석 절차를 함께 제공한다.

### 1.3 AI와 가설을 다듬은 과정 및 채택 근거

과제의 요구대로 측정 가능성, 짧은 기간 내 실행 가능성, 기각 시에도 해석할 수 있는지를 기준으로 질문을 좁혔다. 처음의 "어느 자료구조가 빠른가"라는 넓은 질문은 **조회 대상이 존재하지 않는 경우**, **크기 세 단계**, **동일 정수 집합**, **실행 시간 중앙값**이라는 관찰 가능한 조건으로 구체화했다. AI는 측정 설계·코드·결과 요약과 후보 비교를 도왔고, 연구는 가설이 틀린 결과가 나오더라도 그대로 기록하도록 설계했다. 최종 채택 근거는 외부 가입·비밀키 없이 순수 Python으로 재현할 수 있으며 데이터도 직접 생성·측정할 수 있다는 점이다.

### 1.4 최종 가설과 반증 조건

**H1: 서로 같은 정수 n개(n = 100, 1,000, 10,000)를 각각 보유한 Python `list`와 `set`에서 존재하지 않는 값 -1을 조회할 때, 모든 n에서 `set`의 30회 측정 중앙값(ns/조회)이 `list`보다 작다.**

- **독립변수:** 자료구조 종류(`list`/`set`)와 원소 수(n). 추가 탐색 조건은 부재/첫/끝 위치.
- **종속변수:** `timeit.Timer("needle in container").timeit(number=loops)/loops × 10⁹`, 단위 ns/조회.
- **반증 조건:** 지정한 크기 가운데 **하나라도** 부재 조회에서 `set` 중앙값이 `list`보다 크거나 같으면 H1을 지지하지 않는다.
- **범위:** 정수 0부터 n-1까지를 넣은 각 컨테이너, 2026년 10월 9일 단일 측정 환경, 조건마다 반복 측정 30회. 외부 데이터 수집이 아닌 직접 생성된 입력 데이터의 실험이다.

## 2. 선행 문헌과 논거

Python Software Foundation(2026a)은 `in` 연산이 컨테이너에 대한 원소 포함 여부 확인이라는 점을 규정한다[1]. Python Software Foundation(2026b)은 `set`이 중복 제거와 **원소 존재 여부 조회**에 활용되는 구조임을 설명한다[2]. Python Wiki contributors(n.d.)는 CPython의 `list` 포함 검사 평균 복잡도 **O(n)**, `set` 포함 검사의 평균 **O(1)**·최악 **O(n)**을 정리한다[3]. 이는 이번 가설의 이론적 배경이지만 실제 상수항과 실행 환경의 결과를 보장하지는 않는다.

측정 방법은 Python Software Foundation(2026c)의 `timeit.Timer` 설명을 따랐고, 측정 잡음과 반복 시행의 중요성은 Georges, Buytaert, Eeckhout(2007)의 실험적 성능 평가 논문을 참고했다[4][5]. Georges 외 연구는 Java 프로그램 벤치마크를 다룬 것이므로 **이번 Python 결과를 선행 연구가 이미 입증했다고 주장하지 않는다.** 본 연구의 새로운 부분은 고정된 Python 입력과 단일 환경에서 3×3×2 조건을 직접 측정하고, 반례에 가까운 첫 위치 검색까지 원자료로 공개했다는 점이다.

**실재·내용 확인 방법:** [1][2][4]는 Python 공식 문서의 각 정의·인터페이스 설명을 확인했고, [3]은 Python 커뮤니티 Wiki의 자료구조별 시간복잡도 표, [5]는 Ghent University 공개 학술 서지에서 저자 3명·발표 연도 2007·학술지·쪽수를 대조했다. 초기에 고려한 "`set`이 언제나 O(1)"이라는 단정은 [3]의 최악 O(n)과 어긋나 **주장 목록에서 제외**했다. 실제 존재하지 않는 논문명·저자명은 인용하지 않았다.

### 3.2 절차 및 자료 보관

1. `reproduce/run_benchmark.py`의 고정 상수로 18개 조합의 자료를 준비한다.
2. 실제 반환값이 참·거짓과 일치하는지 확인하고, 조건별 `timeit` 호출 횟수를 100회 파일럿으로 정한다.
3. 조건별 워밍업 3회를 수행하되 측정 데이터에는 넣지 않는다.
4. 30라운드 동안 각 라운드의 18개 조합을 한 번씩 무작위 순서로 시간 측정한다.
5. `raw_measurements.csv`에 **라운드·크기·조회 조건·자료구조·실제 루프 수·실제 소요 초·조회당 ns**를 행 단위 보관한다.
6. `reproduce/analyze.py`로 모든 원자료를 재계산해 `analysis.json`과 아래 결과표를 검증한다. 중앙값의 비율을 계산하며, 2,000회 재표집 구간은 동일 30라운드 안의 변동 폭 참고용으로만 해석한다.

자료구조를 만드는 시간은 조회 시간에 포함하지 않았다. 이 연구는 **기존 자료에서 반복 조회**하는 사용 맥락에 한정한다. 설계 변경 이력: **없음**. 결과에 유리하도록 원자료를 제거하거나 사후에 H1 조건을 좁히지 않았다.

### 4.2 가설과 일치한 부분

- **부재 조회 100개:** `list` **506.80ns**, `set` **17.65ns**, `list/set` **28.71배**.
- **부재 조회 1,000개:** `list` **6,066.55ns**, `set` **18.31ns**, **331.38배**.
- **부재 조회 10,000개:** `list` **64,935.15ns**, `set` **18.13ns**, **3,581.19배**.
- n이 100→10,000으로 커질 때 부재 조회의 `list` 중앙값은 **128.13배**, `set` 중앙값은 **1.03배**로 변했다. 순차 검색과 해시 기반 조회의 기대 성질에 부합한다.

### 4.3 가설과 다르거나 일반화를 제한한 결과

- **첫 위치 조회**는 n=100, 1,000, 10,000에서 `list/set` 비율이 **1.04, 1.00, 1.02배**로 매우 근접했다. 특히 n=1,000에서 `list` 중앙값 **17.984ns**가 `set` **17.988ns**보다 조금 작았다. 이 차이는 런타임/반복 잡음보다 작아 승패를 일반화할 수 없다.
- **마지막 위치 조회**의 비율은 n=100에서 **28.03배**, 1,000에서 **248.12배**, 10,000에서 **2,665.70배**. 부재 조회와 유사한 패턴이지만, 마지막 원소가 `set` 내에서 일으키는 해시/탐색 비용 및 런타임 조건 차이로 정확한 배수는 같지 않았다.
- `set`이 매 조회에서 항상 더 빠르거나, 모든 연산이 최악 O(1)이라는 가설은 검증 대상도 아니며 이번 자료는 이를 뒷받침하지 않는다.

### 4.4 예상과 다른 결과에 대한 가능한 설명

1. **첫 위치 조기 종료:** `list`는 첫 원소에서 바로 일치하면 전체 길이와 관계없이 검사를 끝낼 수 있다. 자료구조 크기만으로 시간을 예측하면 오류가 생긴다.
2. **타이머·실행 오버헤드:** 매우 짧은 조회에서는 반복문·타이머·인터프리터 비용이 실제 자료구조 간 차이를 가릴 수 있다. 분포의 하한과 중앙값을 모두 확인해야 한다.
3. **캐시·해시 슬롯·스케줄링:** `set`의 특정 정수에 대한 해시 슬롯 접근과 OS 프로세스 간섭이 미세 차이를 만들 수 있다. CPU 프로파일러나 여러 시스템이 없으므로 원인을 단정하지 않는다.

## 5. 논의

### 5.1 가설 판단

**최초 H1을 이 실험 범위에서 지지한다.** 세 자료 크기에서 없는 정수 -1을 찾을 때의 `set` 중앙값이 모두 `list`보다 짧았다. 모든 데이터 행을 분석에 포함했고, 크기별 전체 30개 블록의 원자료는 패키지에 실었다. 이로부터 반복되는 **부재 조회**가 많은 CPython 작업에서는 기존 자료를 `set`으로 보관하는 선택이 유리할 수 있다고 말할 수 있다. 다만 자료구조 생성 시간이나 자료의 순서 보존 요구가 있는 실제 애플리케이션에는 직접 적용할 수 없는 조건부 결론이다.

### 5.2 한계

첫째, **한 번의 측정 세션·한 CPU 환경·CPython 3.13.5**의 숫자이므로 다른 환경의 절대 지연·비율을 보장하지 않는다. 둘째, 동일 정수 0…n-1만 사용해 문자열, 객체의 `__hash__`·`__eq__`, 충돌 사례, 메모리 사용량은 측정하지 않았다. 셋째, 이미 만들어진 컨테이너의 조회만 측정해 리스트를 세트로 변환하는 비용, 삽입·수정·순서 요구는 포함하지 않는다. 넷째, 파일럿으로 각 조건의 측정 루프 수가 달라져 잡음 민감도가 다를 수 있다. 다섯째, 30라운드는 한 프로세스에서 측정된 블록으로 완전히 독립인 540개의 서로 다른 머신 실험이 아니다. 통계적 재표집 구간은 광범위한 성능 보증이 아니다.

### 5.3 후속 연구

복수 프로세스/CPU에서 반복, 문자열·해시 충돌 등 입력 다양화, `set` 구축+조회 총비용 분석, 메모리 사용량 측정, 실제 웹 서비스의 조회 분포 관찰을 제안한다. 이는 후속 제안일 뿐 본 논문에서 수행한 결과가 아니다.

## 6. 결론

동일 환경의 정수 컨테이너에서 부재 조회를 반복하면 `set`이 `list`보다 빠르다는 가설은 세 크기 모두에서 지지됐다. 특히 자료가 10,000개일 때 `set` 약 18ns 대비 `list` 약 64,935ns라는 큰 차이가 있었다. 그러나 `list`의 첫 원소를 찾는 경우에는 차이가 거의 사라졌고 크기만으로 전체 작업 성능을 판단할 수 없었다. 이 실험에서 얻은 핵심은 "`set`이 무조건 빠르다"가 아니라, **자료 크기와 조회 성공·실패 위치에 따라 적합한 자료구조를 선택해야 한다**는 조건부 결론이다. 프로젝트에서 자료구조를 선택할 때 실제 데이터의 특성과 주요 사용 패턴을 먼저 확인하고, 작은 실험으로 가정을 검증하는 개발 방식을 유지하고자 한다.
